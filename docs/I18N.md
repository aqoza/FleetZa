# Internationalization & RTL

FleetManage ships English + Arabic with full right-to-left support. The system is
**type-safe** and **module-scoped** so every new feature is translatable and
direction-correct by default. This doc is the contract for adding strings, modules,
and languages.

## How it works

- `src/i18n/index.tsx` — the engine. Merges every namespace into `en` / `ar`
  dictionaries, derives `MessageKey` (the union of all English keys), and exposes
  the `I18nProvider`, `useI18n()` and `useT()` hooks.
- `src/i18n/messages/{en,ar}/<namespace>.ts` — the dictionaries. One namespace per
  module. Each `ar/<ns>.ts` is typed `Translation<typeof en<Ns>, "ar">`, so a
  missing Arabic translation (or a missing Arabic plural form) is a **compile
  error**. String-only namespaces still typed `Record<keyof typeof en<Ns>, string>`
  are equivalent; switch them to `Translation` when they gain a plural.
- `src/i18n/plural.ts` — plural forms: the per-language CLDR category table and
  the `Translation` / `PluralForms` types (see [Plurals](#plurals-counts)).
- Direction: Arabic sets `<html dir="rtl">`. Layout follows via Tailwind **logical
  utilities** — never hardcode a physical side.
- Language persists to `localStorage` (instant, pre-login) and to
  `profiles.language` for signed-in users (synced by `AuthContext`).
- Formatting (money, dates, numbers) stays driven by the tenant **country locale**
  (`shared/countries.ts`) and keeps Western/Latin digits for business clarity —
  independent of UI language.

## Using strings in a component

```tsx
import { useT } from "@/i18n"; // or relative path
function MyThing() {
  const t = useT();
  return <button>{t("vehicles.add")}</button>;
}
```

Interpolation: `t("sales.toast.invoiced", { number: "INV-0042" })` where the value
is `"Invoice {number} created."`. A number that changes the words around it is
not interpolation — use a [plural message](#plurals-counts) and `tp()`.

Enum labels come from `src/lib/labels.ts` as translation keys:
```tsx
<Badge tone={vehicleStatus[v.status].tone}>{t(vehicleStatus[v.status].labelKey)}</Badge>
```

## Plurals (counts)

**Rule: if a number in a message changes the words around it in *any* language,
the message is a plural message and renders with `tp()`.** Never
`t(key, { count })` for a counted noun, and never branch on the count yourself
(`n === 1 ? keyOne : keyMany`): English has two forms, Arabic has six.

A plural message is an object of CLDR plural forms instead of a string:

```ts
// en/vehicles.ts — English needs `one` + `other`
"vehicles.countInFleet": {
  one: "{count} vehicle in your fleet",
  other: "{count} vehicles in your fleet",
},

// ar/vehicles.ts — Arabic needs all six
"vehicles.countInFleet": {
  zero: "لا توجد مركبات في أسطولك",
  one: "مركبة واحدة في أسطولك",
  two: "مركبتان في أسطولك",
  few: "{count} مركبات في أسطولك",
  many: "{count} مركبة في أسطولك",
  other: "{count} مركبة في أسطولك",
},
```

```tsx
const tp = useTp();
tp("vehicles.countInFleet", vehicles.length);                    // "3 vehicles in your fleet"
tp("insights.inShop", inShop, { total: fleet.length });          // other placeholders as usual
tp("fuel.logCount", total, { count: formatCompact(total) });     // "1.2K fuel logs"
```

- `tp(key, count, vars?)` picks the form with `Intl.PluralRules(language)` and
  fills `{count}` with `count`. The plural selector is **always `{count}`**, so name
  the counted placeholder `count` (not `days`, `minutes`, `total`…). Passing
  `count` in `vars` changes only what is displayed, never which form is picked.
- **Compile-checked.** `t()` accepts only string keys (`MessageKey`); `tp()` accepts
  only plural keys (`PluralKey`). An English plural missing `one`/`other`, or an
  Arabic one missing any of its six forms, fails `tsc`. Turning a string into a
  plural therefore flags every `t()` call site that still uses it.
- Outside React: `translatePlural(key, count, vars)`, and
  `translatePluralIn(language, key, count, vars)` for a fixed language (bilingual
  documents, tests).
- `src/i18n/plural.test.ts` checks every plural in both dictionaries against
  `Intl.PluralRules` and verifies that no form uses a placeholder its English
  message lacks.

### When is a message plural?

- **Counted nouns and agreeing verbs:** "{count} drivers", "{count} renewals are
  overdue", "Renew {count} certificates". Plural.
- **Arabic-only inflection:** abbreviated English like `"Due in {count} d"` or
  `"{count} min"` never changes, but the Arabic noun does (يومين، أيام، يومًا).
  Still plural, with identical English `one`/`other` forms.
- **No counted word:** `"{count} selected"`, `"Skipped ({count})"`,
  `"{done} of {total} done"`, `"{from}–{to} of {total}"`. Plain `t()`.
- **Constants:** a cap that is always large, like `"Only the first {count}
  matching vehicles are shown"` with 200, is always the same form. Plain `t()`.
- **Two counts in one message:** pluralise on the count whose noun is written
  out (e.g. `bulkDonePartial` pluralises on the batch size), and pass the other
  counts as ordinary `vars`.

### Writing the Arabic forms

Numbers stay Western digits (see [How it works](#how-it-works)). The noun after
a number changes with it:

| Category | Numbers | Noun form | Example (مركبة / يوم) |
|---|---|---|---|
| `zero` | 0 | Free phrasing, usually «لا توجد …» | لا توجد مركبات · اليوم |
| `one` | 1 | Singular, usually + واحد/واحدة, number dropped | مركبة واحدة · يوم واحد |
| `two` | 2 | Dual, number dropped | مركبتان · يومين (after a preposition) |
| `few` | 3–10, 103–110, … | Plural | {count} مركبات · {count} أيام |
| `many` | 11–99, 111–199, … | Singular, accusative (tanwīn on masculine nouns) | {count} مركبة · {count} يومًا |
| `other` | 100–102, 200–202, … and fractions | Singular | {count} مركبة · {count} يوم |

- The dual takes its case from the sentence: «مركبتان في أسطولك» (nominative), but
  «خلال يومين» and «منذ يومين» after a preposition.
- `zero`, `one` and `two` may drop `{count}`, because the words carry the number.
  English has no zero category: `0` uses `other` ("0 vehicles"). If an English
  empty state needs different wording, give it its own string key.
- A partitive phrasing («{count} من التجديدات متأخرة») is correct for every count
  from 3 up, so `few`/`many`/`other` can share it.

## Adding a new module (future features)

1. Create `src/i18n/messages/en/<module>.ts`:
   ```ts
   export const en<Module> = { "<module>.title": "Title", ... } as const;
   ```
2. Create `src/i18n/messages/ar/<module>.ts`:
   ```ts
   import { en<Module> } from "../en/<module>";
   import type { Translation } from "../../plural";
   export const ar<Module>: Translation<typeof en<Module>, "ar"> = { "<module>.title": "…" };
   ```
3. Register both in `src/i18n/index.tsx` (one import + one spread in `en` and `ar`).
4. Prefix keys with the module name to avoid collisions (`vehicles.*`, `fuel.*`).
5. Any count string is a [plural message](#plurals-counts) from the start.

That's it — `t()` and `tp()` autocomplete the new keys, and TS forces the Arabic
side complete.

## Adding a new language

Add the code to `Language` and `LANGUAGES` in `src/i18n/index.tsx`, add its CLDR
plural categories to `PLURAL_CATEGORIES` in `src/i18n/plural.ts` (the test pins
them to `Intl.PluralRules`), create `src/i18n/messages/<lang>/*.ts` typed
`Translation<typeof en<Ns>, "<lang>">`, register them, and set `dir` if the
script is RTL. The migration `check (language in (...))` on `profiles.language` must
be widened too.

## RTL rules (apply in every component)

Use **logical** Tailwind utilities so layout mirrors automatically. Never use the
physical variants below on the left column:

| Physical (avoid) | Logical (use) |
|---|---|
| `pl-`, `pr-` | `ps-`, `pe-` |
| `ml-`, `mr-` | `ms-`, `me-` |
| `left-`, `right-` | `start-`, `end-` |
| `text-left`, `text-right` | `text-start`, `text-end` |
| `rounded-l-`, `rounded-r-` | `rounded-s-`, `rounded-e-` |
| `border-l`, `border-r` | `border-s`, `border-e` |

- **Direction-bearing icons** (back arrows, chevrons, "next/prev") must flip:
  add `rtl:-scale-x-100` to the icon (or swap `ChevronLeft`/`ChevronRight`).
- **Charts** (recharts) read left-to-right even in Arabic — wrap chart containers
  in `<div dir="ltr">` so axes/legends stay sane.
- `gap-`, `flex`, `grid`, `justify-between` are already direction-agnostic — leave them.
- `flex-row` reverses automatically under `dir="rtl"`; rely on that instead of
  reordering DOM.

### Left-to-right data (bidi isolation)

On an Arabic page the Unicode bidi algorithm reorders values that are not
Arabic prose: the phone `+1 702 555 0133` renders as `0133 555 702 1+`, and
`Gulf Freight Co.` as `.Gulf Freight Co`. Isolate every data value that is
rendered as text, using the primitives in `src/components/ui.tsx`:

| Value | Use | Why |
|---|---|---|
| Phone, email, URL/website, plate, VIN, chassis/engine/serial number, document number (`QUO-00012`, `RSL-2026-…`), SKU, CR/tax number, IBAN, UIN, PO/reference number, postal code, code-like IDs | `<Ltr>{value}</Ltr>` | Always left to right, and often has no letters to decide by — a phone is all digits and neutrals, so only a forced direction fixes it. |
| User-entered text in an unknown script: customer, vehicle, driver, product and technician names, titles, addresses, notes shown inline | `<Bdi>{value}</Bdi>` (`<bdi>`) | Direction comes from the text's first strong character: `Gulf Freight Co.` keeps its period, an Arabic name stays right to left. |
| Money, distances, volumes, dates, date-times and compact numbers from `src/lib/format.ts` | `<Ltr>{formatMoney(…)}</Ltr>` | Formatting uses the tenant's `en-<CC>` locale in both UI languages, so the output is always Latin: `84,210 km` otherwise renders as `km 84,210`, `Sep 24, 2026` as `2026 ,24 Sep`. The formatters stay pure — CSV, PDF and chart code use them too. |
| Translated UI strings | nothing | Already in the page's language. |

- **Tables:** set `dir: "ltr"` or `dir: "auto"` on the `DataTableColumn`
  instead of wrapping inside `cell`.
- **Pickers:** `Combobox` isolates option labels (`<bdi>`) and forces `meta`
  LTR; set `metaDir: "auto"` on an option whose meta is a name, title, model or
  translated text.
- **Headers:** `PageHeader` wraps its title in `<bdi>`; pass record names as-is.
- **Inputs:** `<Input type="email|tel|url">` is LTR automatically; pass
  `dir="ltr"` for other LTR fields (VIN, plate, IBAN, codes, serials). Every
  other `Input`/`Textarea` takes its direction from its own content
  (`unicode-bidi: plaintext`), so a Latin name being edited reads correctly and
  Arabic stays right to left.
- **Truncated values** (`truncate`): an isolate inside an RTL block overflows
  at its start ("…mo Owner"). Truncate the value in its own direction, inside a
  flex row that keeps it at the page's start edge:
  `<div className="flex"><span dir="auto" className="truncate">{name}</span></div>`
  (`dir="ltr"` for identifiers). Don't put `dir` on the block that aligns the
  text — `text-start` and logical spacing (`ms-`, `ps-`) resolve against the
  element's own direction and would jump to the other side.
- Both primitives are inline: the text keeps the cell's `text-start`/`text-end`
  alignment. Never force `dir="ltr"` on a block, a cell or a label — only on the
  value — and never wrap block content (`<div>` stacks) in them: inner blocks
  would inherit the value's direction and align to the wrong side. Wrap the
  text inside instead; use a column's `dir` only when its `cell` returns inline
  content.
- Composite strings built in code that join values of different kinds
  (`${plate} · ${name}`) isolate each part. A phrase of one kind — an address
  line "Las Vegas, US", "2022 Volvo FH16" — stays whole in one `<Bdi>`:
  splitting it reverses its parts on an Arabic page.
- **Strings, not elements:** where only a string fits — a value interpolated into
  a translated sentence (`t("x.deleted", { name: bdiText(name) })`),
  `window.confirm()` — use `ltrText()` / `bdiText()` from `src/lib/bidi.ts`
  (Unicode isolates). Never for values that leave the screen or are matched:
  CSV, clipboard, URLs, file names, form values, PDF documents, `aria-label`.
- **Native `<option>`:** put `dir="auto"` (names) or `dir="ltr"` (codes) on the
  `<option>` — isolate characters at the start of its text break the browser's
  type-to-select.
